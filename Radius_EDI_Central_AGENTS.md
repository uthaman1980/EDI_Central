## Radius product facts: use as integration constraints, confirm on current release
Provided *EDI Tutorial* (43 slides) describes the Radius/XLink conventions below; these are reference behavior, **not proof of the currently deployed Radius 2026.3 configuration**:
- Radius works with flat files organized as batch header, document header, document lines, and batch footer; a translator exchanges these with X12/partner formats. Radius XLink Update is the import/export integration boundary (slides 4–5).
- Inbound EDI message generation/import and subsequent XLink business update may be separate steps; running separately permits validation and correction before posting (slide 26). Support distinctly traceable states for both stages.
- Radius EDI defaults can be overridden per customer/supplier; file folder, basename, extension, format, test flag, sequence-based filenames and activation can vary by partner/message (slides 18–24). The platform must respect both its own central configuration and Radius-side activation/settings; discrepancies should be shown as configuration faults rather than silently changing Radius.
- Inbound XLink options must be active; outbound requirements differ. Test Mode preserves a not-processed state while updating errors; it is **not** equivalent to a successfully posted transaction (slides 6–7, 21).
- XLink batch update uses company number plus four-digit update code: `1xxx` for inbound and `2xxx` for outbound (e.g. `1850`, `2850`); optional `NOTREJ` suppresses rejected reprocessing and `DB` enables audit output. Running with company-only processes all active updates: **never use that unscoped default in a per-capability job** (slides 9–13).
- Radius EDI messages described in the tutorial: inbound 830, inbound 850, inbound 856; outbound 810, outbound 850, outbound 855, outbound 856, outbound 858 (slide 18). These are candidate capability catalog entries, **not automatically supported implementations**. Extend only with verified mappings and integration behavior.
- Outbound trigger points differ: 810 from billing, 850 from printed PO, 855 from acknowledgment/appropriate shipping request change, 856/858 from completed BOL/shipment (slide 32). Never equate “file emitted” with “customer received and accepted.”
- For inbound 850, sales order, shipping request, or both may be generated; customer PO/line references, customer item reference and address references matter; address updates can mutate Radius master data and must require explicit approval/configuration (slides 28–29).
- Tutorial version/settings may be old; validate against the site's current installed Radius version, EDI format documentation, XLink options, and actual DB metadata before implementing commands or write operations.

### Four routing scenarios: encode explicitly (decision table)
| Direction | Partner route | Incoming/produced file | Application responsibility | Exit condition and evidence |
|---|---|---|---|---|
| **INBOUND** | **VAN / EDI provider** | Provider puts a **Radius-expected flat file** in the Radius-designated inbound folder (or an agreed landing folder that feeds it) | **NO translation by default**. Register/discover the file, check path/name/readiness and configured contract, track source, correlate to Radius XLink processing and Radius business result; orchestrate Radius XLink only if configured/authorized. Never interfere with provider's established feed. | File picked up by Radius, XLink parsed, business transaction posted/rejected; log exact outcome. VAN deposit alone is not completion. |
| **INBOUND** | **DIRECT customer** | Customer-origin format (X12, CSV, XML, JSON, Excel, fixed-width, custom flat file, etc.) lands in the configured **customer source directory/endpoint** | **Middleware REQUIRED** unless source is explicitly approved as Radius-ready: read/parse using a **versioned customer + EDI-type + format profile**, validate, normalize/map, generate the precise Radius-expected flat file, publish atomically to that **customer's Radius inbound folder**, then track Radius processing and result. | Customer file -> transformed Radius file -> Radius XLink record(s) -> created/updated Radius business transaction, with lineage and error detail. |
| **OUTBOUND** | **VAN / EDI provider** | Radius creates its standard outbound file in the **Radius EDI message file location** for that customer/EDI type | **PASS-THROUGH / TRACK ONLY**: do **not** transpose, rename, move, delete, or send it by default. The VAN/provider picks it up from the existing Radius folder. Use non-destructive observation (read-only watcher/polling or approved audit feed), capture metadata/checksum/document association/status; integrate pickup/ack proofs *only when available*. Do not race the VAN. | `RADIUS_FILE_CREATED`, then optional `VAN_PICKUP_CONFIRMED` or `ACKNOWLEDGED` if supported; otherwise `AWAITING_EXTERNAL_PICKUP`/`PICKUP_UNVERIFIED` rather than falsely reporting delivery. |
| **OUTBOUND** | **DIRECT customer** | Radius creates its **standard outbound flat file** in the customer/type Radius output folder | **Middleware REQUIRED**: observe/claim through a carefully approved non-disruptive handoff, parse Radius format, normalize, apply customer's **versioned outbound format/mapping**, serialize as required (X12/CSV/XML/etc.), write to a **separate customer delivery/output location** (or approved SFTP/AS2 delivery later), atomically publish and track transfer/receipt. Never overwrite the original Radius export. | Radius file -> partner-specific file -> successfully published to configured customer destination; record receipt/ack only if independently verified. |

**Critical distinction:** Route class (`VAN` versus `DIRECT`), direction (`INBOUND` versus `OUTBOUND`), file contract (`RADIUS_FLAT` versus `PARTNER_FORMAT`), and **processing strategy** (`PASSTHROUGH_TRACK`, `TRANSLATE_TO_RADIUS`, `TRANSLATE_FROM_RADIUS`) are independent, typed, validated attributes. A VAN feed can use various communications technologies; `VAN` is not a synonym for SFTP. An explicit optional override may use translation for a provider file ONLY if the provided artifact is not Radius-ready and this is verified/configured. Maintain separate `RadiusInboundFolder`, `RadiusOutboundFolder`, `PartnerInboundLandingFolder`, and `PartnerOutboundDeliveryFolder`; do not use one ambiguous `FilePath` field. Customer × message type × direction × environment × route/profile define the effective paths. A customer can use VAN for one capability and DIRECT for another, or have separate distinct routes for each.

### Routing, file ownership, and observer safety
- **Radius owns its EDI file generation/import contract**, active messages, format and generated naming/sequence; the new app configures/correlates this, but must not silently rewrite Radius settings. Radius configured path can be a UNC Windows share accessible to Radius or an alternate worker; test service-account access independently.
- **VAN inbound**: do not claim/move an input file away from Radius when Radius/provider already owns it; use read-only observation or a cooperative handoff. If the VAN drops files into a middleware-managed staging area instead, the application may *reliably copy/publish unchanged* to the verified Radius inbound path as an explicit configured `COPY_RADIUS_READY` mode, never silently assumed.
- **VAN outbound**: external provider owns pickup; central app is an **observer**, not a sender. No file deletion/move/rename, including after a hypothetical acknowledgment, unless explicitly agreed in operations contract. File disappearance is not proof of successful VAN pickup; label inference separately from positive provider receipts.
- **Direct inbound**: app owns the partner landing/working/quarantine folders and the file it creates for Radius; publish via temp + atomic rename where filesystem supports it, stable-file checks, duplicate detection and a durable publish ledger. Preserve original customer file and converted Radius file with linkage.
- **Direct outbound**: preserve Radius-original file; coordinate with any existing Radius cleanup or other consumer before watching it; use immutable snapshot/copy or a formally agreed claim mechanism to protect against races. App owns translated delivery artifact and its staging/failed/sent archive. Mark `PUBLISHED_TO_CUSTOMER_FOLDER`, not `CUSTOMER_RECEIVED`, when only a shared folder write is known.
- The same file may contain multiple business documents; create records and correlation IDs for source artifact, transformed artifact, Radius XLink batch/record and each SO/SR/ASN/invoice/BOL. Use partner/customer and type-specific filename masks, sequence awareness, checksums and semantic deduplication. Do not derive EDI identity solely from filename.
- **Disable/enable** semantics per customer + capability + route: disabled means no new transformation, posting, or optional delivery; optionally preserve observational tracking of VAN/Radius files under a distinct `MonitorOnly` setting. Do not deactivate native Radius EDI automatically when central tracking is disabled.

## Architecture targets

Separate (a) configuration/API and UI, (b) scheduler/orchestrator, (c) transport/file intake & delivery, (d) translator/parser/serializer, (e) trading-partner normalization/validation/mapping, (f) Radius XLink/ERP integration, (g) transaction store/audit and alerting. Reuse existing code, auth, ORM, DB, UI framework, and CI where sound; document deviations.

- `TradingPartner` / `Customer`: Radius CompNum, PlantCode where relevant, Radius customer code, EDI ID/qualifier, X12 ISA/GS identity as appropriate, display name, active flag, support contacts, default timezone, ownership, operational tags; distinguish legal customer from partner route if needed.

- `PartnerCapability`: unique by environment + partner + message + direction + version/route where appropriate; enable/disable/test status, schedules, parser/mapper version, Radius company/plant, profile, duplicate rules, auto-post/manual approval, error/notification options, effective dates.
- `Endpoint` / `Route`: owned by partner capability or reusable via explicit association; transport (`LOCAL_FOLDER`, `UNC`, `SFTP`, `AS2`, `API`, future VAN), inbound path, outbound path, ready/staging path, archive, error, quarantine, credentials as **secret references**, permissions and health check; allow fully distinct locations per customer and document direction. - `TradingPartnerMap`: partner identifiers, customer SKU -> Radius item/Customer Item Ref, units of measure, warehouses/plants, ship-to/bill-to, shipping methods, terms, carrier, record types, code lists, trading-partner exceptions, approval and version history. Scoped to partner + capability + environment as necessary.
- `ProcessingJob` and `ExecutionRun`: periodic schedule, worker leases, start/end, trigger (scheduled/manual/retry), node, heartbeat, counters, result, version.
- `FileArtifact`: original immutable file identifier/hash, byte count, source and destination, basename, receive/publish timestamps, safe archived location, parse outcome and linked jobs; preserve raw payload according to retention policy.
- `Interchange` / `FunctionalGroup` / `DocumentTransaction`: X12 envelope IDs (ISA13, GS06, ST02), set/version, partner direction, customer PO, SO, SR, BOL, invoice, ASN identifiers, Radius XLink/staging keys, business result, timestamps and acknowledgments. Include multiple document records per physical file.
- `ProcessingEvent` / `AuditEvent`: append-only timeline including actor, worker, old/new state, reason, correlation ID, redacted detail, trace ID, timestamp. Add `Alert`, `RetryAttempt`, `Acknowledgment`, `ConfigurationVersion` as necessary.

Do **not** conflate a processing file, X12 document, Radius business transaction, or job execution into a single record. Enforce foreign keys and indexes for partner, direction, transaction type, status, business refs, creation time and correlation ID. Use migrations, never runtime schema hacks.

### Processing model: inbound
1. Enabled capability + healthy route + verified partner/RADIUS prerequisites -> scheduler/watch picks up matching file from that partner's configured source. Implement stable-file detection and atomic claim/move/lease to prevent partial reads or double pickup. No recursive accidental reads from archive/output directories.
2. Persist file artifact, hash and source identity, record job and correlation ID **before any business write**. Identify trading partner using configured endpoint and, when X12, sender/receiver IDs; reject/quarantine mismatches (never silently associate with wrong customer).
3. Parse applicable format (raw X12 where supported, VAN-translated intermediary file, or Radius flat file). Validate envelope, segments, required fields and partner-specific profile; support multi-document and multi-interchange files, delimiters, versions, trailers/counts, and escaped content. Fail closed on unsupported format/version.
4. Normalize to a typed canonical message, apply versioned cross-reference tables and business rules. Provide field-level issue reporting and pre-import preview. Avoid guessing missing Radius codes or creating unknown master data without permission.
5. Stage Radius-specific payload according to **actual verified** XLink format/staging contract (do not assume SQL direct writes are safe). For inbound 850 preserve correct order line, PO number, customer-item cross-reference, ship-to/bill-to, quantities/UOM, requested/have-ready dates where applicable, order/shipping request choice, and multi-line transaction integrity.
6. Execute approved, targeted Radius XLink import/update through a controlled adapter, or hand off to existing Radius batch/service configuration. Capture generated XLink IDs, import warnings, rejected rows, Radius SO/SR numbers and posted result. Do not automatically enable XLink or override test mode.
7. Persist precise stage states, archive success files, quarantine validation failures, and move integration failures to retry-safe handling. Generate functional/business acknowledgments only if partner profile requires and corresponding adapter exists.

### Processing model: outbound
1. Identify eligible Radius documents via verified Radius EDI/XLink export, queue or controlled poll/event source; respect native trigger points and customer EDI settings.
2. Read the generated Radius flat file/export record; link to actual invoice/PO/acknowledgment/BOL/SR. Normalize and validate; transform to partner-required version/profile; control file identity, target filename and incremental numbering.
3. Write to capability-specific staging area and atomically publish/deliver to the configured destination (folder/UNC/SFTP/AS2/VAN adapter). Record durable proof of write/transfer, external message ID/receipt when available.
4. Distinguish `EXPORTED`, `TRANSLATED`, `DELIVERED`, `ACK_PENDING`, `ACK_ACCEPTED`, `ACK_REJECTED`, `ACK_TIMED_OUT`. Delivery does not imply business acceptance. Handle X12 997/999 or transport MDN acknowledgments if implemented and partner requires them.
5. No re-emission/overwrite on polling/retry unless a documented idempotent send/resend rule allows it. Support operator-controlled retransmission with audit and new delivery attempt.

### Orchestration and status lifecycle
- Global master toggle and independent per-partner/per-capability **enable**, **disable**, **pause/resume**, plus manual **Run now**, **Test configuration**, **Preview**, **Retry failed**, **Reprocess** with role-based guardrails. Disabling prevents **new claims/sends** but does not silently cancel an in-flight transaction; specify drain/cancel semantics.
- Persist state transitions explicitly, e.g. `DISCOVERED -> CLAIMED -> PARSED -> VALIDATED -> MAPPED -> STAGED -> XLINK_PENDING -> RADIUS_POSTED -> COMPLETED` for inbound; `READY -> EXPORTED -> TRANSLATED -> DELIVERED -> ACK_PENDING -> COMPLETED` for outbound. Include terminal `FAILED_VALIDATION`, `FAILED_MAPPING`, `FAILED_TRANSPORT`, `FAILED_RADIUS`, `QUARANTINED`, `CANCELLED`, `DUPLICATE`, and separate retryable statuses. Implement legal transition rules and immutable event history.
- Scheduling per capability: enabled polling interval/cron/timezone; configurable concurrency, max retries, exponential backoff + jitter, timeout, cutoff/quiet periods, priority. Prevent overlapping executions with DB-backed leases and lease expiry recovery. Follow production load limits for Radius.
- Idempotency: use a composite business key (environment, partner, direction, message type, partner document identity/revision and agreed semantic rules) **in addition to** file checksum; support same filename with new content, re-sent same payload, revised PO, split/multi-doc files, and legitimate 850 order changes. Explicitly choose handling (skip, new revision, quarantine/manual review). Use unique constraints + transactional claims/outbox where appropriate.
- Provide an operator-approved replay from immutable original file with selected mapping version and dry-run option, showing what changes; block duplicate Radius SOs or EDI deliveries.

## File paths, formats, routes
- Windows enterprise deployment is expected; support canonicalized `D:\...` paths and UNC `\\server\share\...` paths from worker hosts. Validate identity's service-account permissions, reachability and atomic-rename support. Do not assume mapped drive letters are available to services.

- Sensitive records: mask PII, customer pricing and credentials in logs; encrypt transport secrets and secret refs; TLS/SSH verification, AS2 signing/encryption/MDN validation when applicable; do not commit sample production data or passwords.

## Acceptance tests that prove the enterprise design
- **VAN inbound:** ingest/observe already Radius-formatted provider file and correlate XLink result with zero translation, no unintended move/delete, preserving Radius/VAN ownership.
- **VAN outbound:** observe Radius-generated file without moving, renaming, rewriting, translating, sending, or consuming it; leave pickup to VAN and display `PICKUP_UNVERIFIED` unless independent proof exists.
- **DIRECT inbound:** read Niagara/customer-specific original format, map to verified Radius inbound flat-file layout, publish to correct customer/type Radius path, track Radius posting and source-to-result lineage.
- **DIRECT outbound:** translate a Radius standard exported file into one partner-required format, publish to distinct partner output folder, preserve Radius original, and never call mere publication acceptance.
- One customer uses VAN for inbound 850 and DIRECT for outbound 856, each with distinct paths and settings; another uses DIRECT inbound 850 with a different schema. No cross-customer pickup or hardcoded routes.
- Create two distinct customers (Niagara and a synthetic TEST customer). Give each different inbound 850 watch folders, mappings, schedules and Radius customer codes. Enable only Niagara: only Niagara messages process; no second-customer pickup.
- Enable the second customer's inbound 850 without redeployment; process both isolated streams concurrently. Disable one: it stops picking up new files while the other continues.
- Enable an outbound 856 for one customer with a separate outbound directory, different from that customer's inbound directory and another customer's output; observe BOL/RADIUS export -> transformation -> atomic delivery -> status/audit. If no verified outbound adapter exists, test with a simulator and label it non-production.
- One inbound file containing multiple orders creates separately traceable documents; a duplicate resend cannot create a second SO; a corrected/changed order follows documented revision behavior.
- Malformed file, unknown customer, missing item mapping, network loss, inaccessible UNC share, Radius rejected XLink record, partial worker crash and outbound transfer timeout each yield visible, actionable, correctly scoped errors; retries never produce duplicate Radius records or untracked transfers.
- User opens transaction and sees the original file, customer, EDI type/direction, run, mapping version, error history, exact Radius SO/SR/ASN/invoice/BOL reference if one exists, and outbound delivery/ack state if applicable.
- Normal Viewer cannot edit routes, replay documents, read secrets, run live posting or activate capabilities. All sensitive actions are audited.
- Shadow-migrated Niagara processing matches the original application on approved fixtures and validated UAT transactions; legacy and new schedulers never post the same document twice.

## Working rules for Codex
- Begin with repository discovery and written findings; **then implement** in small vertical slices. Do not ask for an extensive rewrite before delivering a working foundation.
- Keep the architecture multi-customer and multi-capability from the first DB migration; **never** scatter customer names, directory constants, or 850-only assumptions through core services. Use per-customer configuration and capability adapters.
- Do not run against LIVE without explicit authorization. Never alter, delete or bulk-reprocess live Radius documents as a side effect of building/testing.
- Write tests with each feature; keep existing Niagara behavior and routes working until UAT and cutover sign-off.
- On unknown Radius schemas, business rules, partner implementation guides or credentials: log a `BLOCKER` with precise evidence needed and build a safe interface/mock for tests. **Do not invent integration success or synthetic production data**.
- Provide incremental status with what was actually opened/implemented/tested, exact commands used, test results, blockers, and next steps.
