# Security and access

The workstation's requested login and TEST ODBC credentials are held in ignored `run-web.local.bat`, which `run-web.bat` loads at startup. The committed example leaves passwords blank. Managed deployment should provide credentials through its approved secret source. The current web app uses one HTTP Basic administrator identity and CSRF tokens; it binds to loopback by default. Remote access needs HTTPS reverse proxy and enterprise identity/role integration. **BLOCKER:** SSO and per-role authority are not present, so this is not yet an enterprise multi-user deployment.

Central route mutations require authentication and CSRF. TEST VAN read-only observation is available; LIVE observation additionally requires `EDI_CENTRAL_LIVE_OBSERVATION=1` at activation and each scan, reflecting the user's explicit LIVE Niagara monitoring authorization. Allowed absolute roots are checked at activation and scan time. A partner pause disables its capabilities. An observer does not write to Radius/VAN-owned folders and skips symlink files. This observation permission does not enable LIVE REST submissions. Source paths, customer price data, and decoded Radius payloads are sensitive; restrict SQLite, archives, and `state/radius-debug.log` through service-account ACLs and retention. The existing REST URL uses HTTP on the internal TEST network; **TO VERIFY** approved transport protection and enterprise deployment controls with infrastructure/Radius owners.

External folder contracts and Radius activation flags are operator-reported until an approved read-only Radius configuration interface exists. No native Radius schema write or broad XLink batch call is implemented.
